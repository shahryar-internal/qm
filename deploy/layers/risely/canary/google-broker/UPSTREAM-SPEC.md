# Google broker upstream specification

## Current blocker

The layer contracts in this directory are provider-free validators, cryptographic inspectors, and bounded untrusted projection-shape inspectors. They do not have authority to read QM's encrypted keychain, refresh a Google token, call Google, mutate durable authority state, sign a receipt, or obtain trusted current time. A correctly signed authority envelope and read receipt therefore remain explicitly `usable: false`; no exported function can mint usable authority or evidence. The existing personal Google OAuth connection cannot be used by the CEO canary through this layer.

The current alternative is not an acceptable shortcut. `src/core/orchestrator.ts:1085-1092` decrypts a personal, default, or company connector access token and injects it into a DM turn as `VAULT_TOKEN_*`. The selection is fallback-based rather than an exact provider subject and mailbox binding. `src/core/orchestrator.ts:1230-1260` describes the existing signed credential broker, but `src/api/routes/credentials.ts:7-24` serves org service credentials, not personal connector OAuth. Its request accepts a caller-selected method and URL, so it cannot provide the closed Google operation surface defined here.

Google's default consent in `src/connectors/oauth.ts:215-262` requests `gmail.modify`, full Calendar, Drive, Sheets, Tasks, `openid`, and `email`. That is broader than this read canary. The exchange only decodes an ID token for a company hosted-domain comparison at `src/connectors/oauth.ts:155-173`; it does not cryptographically verify and persist `sub`, verified email, and mailbox as the account identity. Tokens and refresh tokens are encrypted at rest in `src/credentials/keychain.ts:574-607`, decrypted at `src/credentials/keychain.ts:618-627`, and refreshed and rewritten at `src/credentials/keychain.ts:645-699`. Local revoke at `src/api/routes/connectors.ts:412-448` deletes records but does not call Google's revocation endpoint.

Strict posture does not turn the current connector path into a broker. It removes connector injection only when the turn is read-only and otherwise approval-gates tool execution. A proactive scheduled DM can still reach the raw-token injection branch after approval. A standing `tool:execute` approval would be broader than a Calendar/Gmail source grant and would not bind an account, request, lease, or response receipt.

## Required core change

Add a broker-owned logical Google connection record. It must be keyed by organization, credential owner, Google `sub`, normalized verified mailbox, account type, OAuth client reference, and monotonically increasing credential version. It may reference the existing encrypted host token records during migration, but the broker must select the token internally and must never return an access token, refresh token, Authorization header, provider URL, or arbitrary method to a caller. A grant must bind one logical connection version, so a Calendar operation and a Gmail operation cannot silently select different accounts.

Change these core files:

- `src/connectors/oauth.ts`: define a least-privilege broker consent profile with `openid`, `email`, `https://www.googleapis.com/auth/calendar.events.readonly`, and `https://www.googleapis.com/auth/gmail.readonly`. Keep `https://www.googleapis.com/auth/gmail.compose` out of the read profile. Cryptographically validate the ID token issuer, audience, signature, expiry, nonce, `sub`, `email`, and `email_verified`, or retrieve the same identity from Google's authenticated userinfo endpoint. Persist granted scopes and reject a missing scope. A future draft profile adds only `https://www.googleapis.com/auth/gmail.compose` through incremental consent.
- `src/credentials/keychain.ts`: add internal-only token materialization by exact logical connection ID and credential version; preserve single-flight refresh; rotate the credential version when account identity, client, refresh material, or scope set changes; mark refresh failures unavailable without returning a stale token; expose no secret-bearing return type to routes. On Google 401, perform at most one synchronized refresh and one exact retry. A second 401 marks the connection unavailable and returns a signed unavailable receipt. `invalid_grant` marks it revoked and revokes every outstanding lease. Never fall back to another account type or mailbox.
- `src/api/routes/connectors.ts`: keep the browser OAuth callback public only for the provider redirect, validate sealed state/PKCE/nonce and the exact redirect URI, then attach the verified account identity. Revoke must first call `https://oauth2.googleapis.com/revoke`, then erase local access and refresh material and atomically revoke grants and leases. If provider revocation is indeterminate, quarantine the connection and deny execution until reconciliation.
- Add `src/connectors/google-broker.ts`: implement the closed operations `google.calendar.events.list`, `google.gmail.messages.list`, and `google.gmail.messages.get`; construct URLs and methods only inside the broker; disable redirects; set bounded connect/header/body deadlines; cap provider bytes before JSON parsing; create the bounded response body and Ed25519 receipt matching this directory. Add future `google.gmail.drafts.create` only after separate compose consent and review.
- Add `src/connectors/google-broker-store.ts`: use PostgreSQL transactions for logical connections, grants, grant versions, leases, service nonces, idempotency keys, rate buckets, attempts, receipts, revocations, quarantines, and reconciliation records. Database `now()` is the sole authority time and every serialized timestamp uses exact millisecond precision. Unique constraints must cover `(service_principal, nonce)`, `(service_principal, idempotency_key)`, receipt ID, lease ID, and draft effect key. Service, lease, and request nonces are independently generated canonical base64url encodings of 32 bytes. A changed request hash under an existing idempotency key is a conflict. Grant revocation and credential-version rotation invalidate leases in the same transaction.
- Add `src/api/routes/google-broker.ts` and register it in `src/api/routes/index.ts`. Route handlers must parse only the strict layer-equivalent schema, resolve the authenticated service principal from the server credential rather than the body, transact the replay/rate/authority checks before provider use, and commit the attempt and receipt before replying.
- `src/api/deps.ts` and `src/wiring.ts`: wire the store, internal keychain accessor, fixed Google executor, receipt signer, and dedicated service verifier. The runtime can receive only `GOOGLE_BROKER_SERVICE_HMAC_SECRET`, `GOOGLE_BROKER_SERVICE_KEY_ID`, `GOOGLE_BROKER_RECEIPT_ED25519_PRIVATE_KEY`, and `GOOGLE_BROKER_RECEIPT_KEY_ID` for this feature. The canary receives only the service HMAC secret and deployment-pinned receipt public key. Neither workload receives the other's signing key.
- `src/config.ts` and `src/deployment/secret-schema.ts`: require the two new core secrets in production, require them to differ from `CORE_SIGNING_SECRET`, `CAPABILITY_SECRET`, `PORTAL_IDENTITY_SECRET`, and every canary ingress secret, validate Ed25519 key type, and publish only the receipt public key and key ID to the deployment layer.
- `plugins/web-ui/src/connectors.ts` and its core bridge: show the verified mailbox, Google subject fingerprint, account type, exact granted scopes, credential version, grant purpose, service principal, job class, allowed operations, creation/expiry, and state. Require explicit confirmation for create, renew, revoke, quarantine release, and future compose elevation. Never render token material.

## Routes and authentication boundaries

Add these exact routes:

- `GET /v1/connectors/google/broker/grants?principalId=...`: source-authenticated portal request plus a valid `x-portal-identity`; the asserted principal must equal the portal principal.
- `POST /v1/connectors/google/broker/grants`: source-authenticated portal request plus portal identity. The body selects an already verified logical Google connection and a closed operation set. It cannot submit a mailbox, subject, credential owner, service principal, or credential version; core resolves those values. This route creates or renews a versioned grant.
- `POST /v1/connectors/google/broker/grants/:grantId/revoke`: the same portal identity boundary, with an atomic durable revoke.
- `POST /v1/connectors/google/broker/leases`: dedicated Google-broker service HMAC only. It resolves the organization, deployment, and service principal from the key ID, accepts a grant ID/version, job ID/class, and request operation, and returns a signed opaque authority envelope containing the exact server-issued grant and lease, five-minute-or-shorter expiry, 32-byte nonce, and PostgreSQL current-time assertion. Raw grant or lease JSON is never authority.
- `POST /v1/connectors/google/broker/read`: dedicated Google-broker service HMAC only. It accepts exactly the opaque authority envelope and a read request from this directory. It rechecks current PostgreSQL time, grant/lease state, membership, credential version, replay, idempotency, and rate limits in the provider-call transaction. It never accepts URL, method, headers, token, provider options, redirects, an account selector, or caller time.
- `POST /v1/connectors/google/broker/verify`: dedicated Google-broker service HMAC only. It accepts a receipt ID/hash and authority-envelope hash, verifies current PostgreSQL time and all durable state without provider access, atomically claims source consumption, and returns the server-signed activation assertion needed before evidence projection. The caller supplies no time. This layer deliberately has no client or usable-authority brand for this route, so activation remains blocked until the upstream implementation and independent review land.
- A future `POST /v1/connectors/google/broker/drafts`: dedicated service HMAC only, disabled until compose consent, effect persistence, reconciliation, and independent review are complete. It accepts the exact proposal schema and never accepts RFC 2822 raw input or provider transport controls.

The service HMAC must not reuse the generic source-auth contract at `src/auth/source-auth.ts:5-73` or `CORE_SIGNING_SECRET`. Add a dedicated verifier that binds version, issuer, audience `google-broker`, deployment key ID, HTTP method, exact path without normalization, PostgreSQL timestamp, 256-bit nonce, content type, decimal content length, and SHA-256 of the exact body bytes. Verify headers before reading the body, stream the body under the schema bound, claim the nonce durably only after the body digest verifies, and map each key ID to one service principal and deployment. Reject query strings, forwarded identity headers, cookies, and browser credentials on service routes.

The grant UI is a browser mutation and must not share the service route. The portal proxy must attach signed portal identity from its server-side session. In addition to existing source authentication and identity checks at `src/api/server.ts:161-303`, grant mutations must require an allowlisted HTTPS `Origin` and a session-bound, single-use CSRF token. Use `SameSite=Lax`, `Secure`, and `HttpOnly` session cookies. A capability token, a request body principal, or source HMAC alone cannot create a personal Google grant.

## Authority, execution, and audit

The transactional authority check must bind organization, deployment, service principal, QM principal, credential owner, Google subject, normalized mailbox, account type, logical credential ID/version, grant ID/version, lease ID/expiry/nonce, job ID/class, operation, purpose, request nonce, idempotency key, and request hash. Grants are bounded to 31 days, leases to five minutes, and boundary comparisons use integer milliseconds. It must reject inactive principals, changed organization membership, absent scopes, wrong account, stale grant or lease, replay, changed idempotency hash, revoked, quarantined, or unavailable state before any provider call.

Rate limits must be durable and checked by service principal, human principal, logical Google account, operation, and job. Persist both denials and calls. Every audit row must contain the complete non-secret binding, server receive/start/complete times, request and response hashes, provider status, refresh attempt and result, redirect rejection, bounded byte counts, outcome, receipt key ID, and receipt ID. Audit values must never contain provider payloads, message bodies, event summaries, addresses, tokens, authorization headers, or client secrets.

Provider execution must use fixed endpoints, query names, methods, formats, page sizes, and time windows represented by the schemas here. Reject every redirect instead of following it. A `google.gmail.messages.get` request must cite a successful signed same-account `google.gmail.messages.list` receipt and its request and response hashes; the listed response must contain the message ID. The get response must contain `INBOX` and must not contain `SPAM` or `TRASH`. Calendar and Gmail results remain external untrusted input after source verification. Evidence must preserve organization, deployment, service principal, QM principal, credential owner, account type, credential ID/version, provider subject/mailbox, grant/version, lease/expiry/nonce, job class/ID, operation, request nonce, idempotency key, request/response hashes, receipt/key IDs, and server observation time. This layer can inspect the bounded shape but cannot emit evidence without the unimplemented trusted-current-time activation.

For future draft creation, compute a domain-separated provider payload hash and effect key from the exact Google account subject/mailbox/account type, normalized recipients, subject, body, evidence hashes, and business key. They exclude credential version, grant, lease, nonces, job, proposal revision, and authorization, so lease renewal cannot change effect identity. A separate authorization hash binds those authority fields and the complete same-account evidence citations. Persist all three hashes before the provider call. A confirmed Google response records `succeeded`. A transport loss after bytes may have reached Google records a signed `outcome_unknown`; it must not retry creation. Reconciliation starts only after both the ambiguous attempt completed and its lease expired, uses actual PostgreSQL received/checked/completed timestamps, and signs the complete prior receipt hash, prior outcome, payload/effect/authorization hashes, account, and durable result. Only a cryptographically verified prior `outcome_unknown` plus `postgresql_committed` `reconciled_absent` permits a separately authorized new attempt.

## Upstream tests required

Add unit and integration coverage beside the new core modules and in `test/connectors.test.ts`, `test/portal-identity-gate.test.ts`, and deployment secret tests. Cover exact scope consent, verified `sub` and mailbox, two connected Google accounts, wrong-account denial, credential rotation, concurrent refresh, `invalid_grant`, one-refresh 401 retry, second-401 unavailable state, provider revocation failure quarantine, redirect denial, provider byte and JSON bounds, exact-millisecond PostgreSQL clock boundaries, 31-day grant and five-minute lease boundaries, fixed nonce encoding, revocation races, replay races across two core processes, idempotent retry, changed hash conflict, Gmail INBOX listing membership and SPAM rejection, rate limits, complete non-secret lineage, draft lease-renewal effect stability, outcome-unknown reconciliation ordering, prior receipt substitution, audit redaction, HMAC key isolation, receipt key pinning and rotation, browser CSRF, portal principal mismatch, and absence of all token material from responses, logs, errors, evidence, and canary environment. Every known failure class needs at least two independent unit, adversarial, or acceptance variants.

The upstream pull request must be independently reviewed. This layer is not an approval of the core design and must remain unavailable until those tests and the deployment secret boundary pass.
