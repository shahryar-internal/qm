# Provider effect policy

This public layer defines the profile-bound write policy and immutable production port requirements. It does not hold credentials, accept caller-supplied ports or trust roots, or contact providers. Production construction accepts only the branded runtime scope and is mechanically unavailable while the immutable profile/catalog trust registry, durable store, provider adapters, and reconciliation ports are absent. The profile's zero provider-grant lifetime is independently denying.

The CEO profile currently has six prospective capabilities in this provider-effect policy catalog. Gmail draft creation, managed primary-calendar create and update, private Notion upsert, and private CEO Slack posting declare automatic mode. Gmail draft send declares an exact one-use approval mode bound to the current draft revision. These modes are hashed policy, not execution authority. Calendar update requires an existing agent-ownership receipt and provider ETag. Notion is fixed to the attested private CEO root. Slack is fixed to the verified CEO direct-message audience. Gmail read evidence remains a source alias that must resolve to the same signed Google subject and mailbox before it can support a write. The profile also declares Mercury invoice creation, but that separate compile-only program remains outside this catalog and explicitly blocked until its exact effect policy and adapter exist.

Every proposal must use the profile's exact provider owner, principal, agent, credential owner, audience, time limit, target, payload, and content hashes. All policies remain non-executable until signed provider identity, durable effect authority, reconciliation, production credentials, and the external activation gates exist. Unknown outcomes are never retried without durable reconciliation.

The provider-free protocol harness under the test tree exercises the future durable contract with fake issuers and ports. It is not imported or exported by the production entry point. An execution caller supplies only a proposal identifier. The durable snapshot must bind the exact profile, policy, capability version, provider operation, provider owner, proposal, strengthened effect identity, provider-eligible evaluation release, provider account, target resource, kill-switch revision, and unconsumed approval when the policy requires one. Kill-switch, evaluation, provider identity, resource ownership, approval, reconciliation identity, and durable receipt records require Ed25519 signatures from distinct, separately classed, capability-allowlisted keys. Resource ownership and reconciliation authentication have bounded lifetimes.

The atomic reservation must persist attempt one in `attempting` state and return the authorization digest, kill-switch revision, evaluation release, provider identity, ownership receipt, approval digest, and approval-consumption time it compared and committed before the effect adapter can receive the proposal. Store and port activation are checked before and after every awaited call. A revocation or kill-switch change before reservation prevents invocation. If adapter liveness changes while an irreversible provider call is awaiting, the network bytes cannot be undone; the durable reservation remains and the result is held as `outcome_unknown` for reconciliation instead of being retried. The future production store must also compare the current kill-switch revision while completing the attempt so a kill-switch change after reservation produces the same hold; no production store or execution path exists yet.

Reconciliation starts only after the original attempt lease expires. It has a separately signed, capability-allowlisted principal and a durable lease bound to the current kill-switch revision, authentication digest, original attempt, and prior receipt. The reconciliation port is a separate type from the mutating effect adapter. It receives a frozen status-query envelope without the proposal payload, must report `read_only_status_lookup` with zero provider mutations, and can resolve the original attempt as verified or failed but cannot issue a replacement attempt. Returned execution and reconciliation receipts are exact, content-addressed, allowlist-verified signed durable records. The existing action tables are not treated as this production store because their current release, receipt, and authority shapes do not prove those requirements.

The inert orchestration constructor exists only under the test tree. The production authority entry point refuses the current shadow profile before any durable or provider call.

New roles reuse `createProviderEffectPolicySuite` with a separately branded deployment profile. Role-specific identities, owners, audiences, grants, and capabilities must remain in that profile; adapters must not add global identity aliases.
