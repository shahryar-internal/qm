# CEO canary schema bootstrap

The CEO canary uses the existing Risely QM PostgreSQL database named `qm`. It does not create or connect to a second application database. Its durable state is confined to the `risely_agent_runtime` schema. `risely_agent_runtime_owner` is a `NOLOGIN` object owner, `risely_agent_runtime_migrator` is an operator-only `NOINHERIT` login allowed only to set that owner role, `risely_agent_runtime_runtime` is the least-privilege application login, and `risely_agent_runtime_evaluation_writer` is a separate `NOLOGIN`-by-default evaluation persistence authority.

The bootstrap creates only those four roles and the dedicated schema in one transaction. It never alters, drops, grants on, or revokes from an existing QM role, schema, table, sequence, routine, or row. It does not revoke `PUBLIC` access from the shared database or its existing schemas. Any preexisting fixed canary role or schema is a hard failure; the script never adopts a prior object or rotates an existing password.

1. Connect directly to the existing Risely QM database as the fixed `qm` database owner. It must be a non-superuser `LOGIN CREATEROLE` role with effective `CREATE` on database `qm`; confirm `SELECT current_database(), session_user` returns exactly `qm, qm`. Terraform binds this trusted administrator to `var.db_username`. The canary owner never receives database `CREATE`.
2. Inventory privileges inherited through `PUBLIC` and database-wide DDL hooks. Standard PostgreSQL `PUBLIC TEMPORARY` is accepted and is not changed here; the canary emits no temporary-object SQL. Every enabled event trigger in `qm` is a hard failure. All fixed roles must have no direct `TEMPORARY` or `CREATE` grant, no effective database `CREATE`, no ownership or `CREATE` on a non-canary schema, no access to non-canary tables or sequences, no ownership or effective `USAGE` of any foreign-data wrapper, no effective foreign-server `USAGE`, and no reachable non-system `SECURITY DEFINER`. `PUBLIC` wrapper `USAGE` fails even if no server exists. If any condition is false, stop. Disabled event triggers and broader cluster state remain explicit infrastructure activation inventory. The inherited `PUBLIC TEMPORARY` capability remains a documented shared-resource risk requiring a separate platform decision if it is to be removed.
3. Run `PGSSLMODE=verify-full PGSSLROOTCERT=/protected/rds-ca.pem PGPASSFILE=/protected/qm.pgpass psql -X --no-psqlrc --host="$CANARY_DATABASE_HOST" --port=5432 --dbname=qm --username=qm --set=canary_bootstrap_admin_role=qm -f migrations/bootstrap.sql` exactly once in that direct creator session. The CA path must contain the reviewed RDS trust bundle; never use `require`, a system-default root store, or an SSL URL query override. Before its first canary DDL, the script refuses a missing or mismatched psql identity, an indirect or superuser session, a creator without `LOGIN CREATEROLE` and database ownership, another database, every enabled event trigger, effective `PUBLIC` foreign-data-wrapper `USAGE`, any preexisting fixed role or schema, incompatible shared authority, or topology drift. It sets `createrole_self_grant` to empty, creates all four roles as `NOLOGIN PASSWORD NULL`, and never reads or changes a credential. PostgreSQL 16 automatically grants `qm` ADMIN-only membership in each role it creates, with role OID 10 as the bootstrap-superuser grantor; a non-superuser creator cannot remove or change those edges. The script grants owner-to-migrator SET-only with `qm` as durable grantor, gives `qm` one temporary SET-only owner edge to create the owner-authorized schema, revokes only that temporary edge, requires exactly the four OID-10 automatic edges plus owner-to-migrator, and commits. An error or rerun rolls the whole structural transaction back.
4. Generate two distinct 32-byte CSPRNG values, encode each as canonical unpadded base64url, and place the resulting exact 43 characters, optionally followed by one LF, into separate owner-only regular files. Build `Dockerfile.db-operator` and launch only its compiled `provision` phase with the dedicated task definition. The provisioner opens each protected path once with nonblocking and no-follow flags, requires a bounded owner-only regular file, validates the two credential encodings and inequality, and passes the already-open passfile and CA descriptors to `psql`; it never reopens those paths after validation. A FIFO is rejected promptly before psql or a database connection. It invokes `psql -X --no-psqlrc` with verify-full TLS and the explicit CA, sends one complete transaction on stdin, repeats each already-validated credential buffer for confirmation, uses SCRAM, enables both logins, rechecks exact topology, commits, requires a nonsecret success marker, bounds child output and time, clears its buffers, and then authenticates both roles over verify-full TLS. Missing, truncated, equal, high-bit, NUL, noncanonical, mixed-state, or malformed input cannot deliver `COMMIT`.
5. Verify the owner and evaluation writer cannot log in, neither provisioned login has an administrative flag or database ownership, and the complete bidirectional membership inventory contains exactly one owner-to-migrator edge plus the four OID-10 automatic edges. Verify no fixed role owns or can create in another schema, can access cross-schema tables or sequences, or can execute a reachable non-system `SECURITY DEFINER`. Runtime and migrator must own no object.
6. Read the structured `ceo_canary_database_environment` Terraform output. It derives `CANARY_DATABASE_HOST`, port, database, and bootstrap administrator directly from the QM RDS resource, but host provenance is not live-attested until a managed CEO-canary task definition consumes that map. Keep activation blocked until task wiring is reviewed. Store query-free TLS runtime and migration URLs matching that contract. Their decoded passwords must be mutually distinct and must also differ from the decoded password in the shared QM `DATABASE_URL`, regardless of username. Never copy the QM application credential or inject the migration URL into ECS.
7. Run the migration image manually with `node /app/canary/service/ceo-canary/src/migrate.mjs`. It accepts only the exact empty bootstrapped schema and no migration history, verifies migrator and owner boundaries, takes the maintenance lock, writes version 8, and rechecks exact catalog, ACL, triggers, ancestry, dependencies, and topology before commit. Standard inherited `PUBLIC TEMPORARY` is allowed; direct temp authority, database `CREATE`, every enabled event trigger, every extra membership edge, cross-schema authority or dependency, an incoming foreign key from another schema, any all-tables publication or subscription relation, extension ownership, schema-less canary cast or transform, foreign-data-wrapper ownership or effective `USAGE`, effective foreign-server `USAGE`, fixed-role or `PUBLIC` user mapping, wrong ownership, and every preexisting ordinary or exotic namespace object fail closed. The version checksum binds the migration, full catalog query and projection, and immutable versioned authority for profile identity, evaluation candidates, signed judge results, provider-ineligible shadow releases, replay tombstones, constraints, indexes, triggers, routines, sequences, relations, columns, types, TOAST relation/index state, and ACL semantics. Sequence 64-bit settings are compared as canonical catalog text. The database migration row is evidence only and cannot authorize drift.
8. Set the sole runtime profile selector `CANARY_DEPLOYMENT_PROFILE_REF` to exactly `deployment-profile:risely:ceo:v1`, connect as `risely_agent_runtime_runtime`, and initialize the store. No legacy Docker principal or identity variables are accepted. Initialization and health verify the same acquired connection, complete bidirectional role topology, direct database ACL, catalog, relation access methods, column collations, extension and dependency ownership, ACL, and shared-database boundary. Each later transaction takes the shared maintenance lock, verifies the lightweight immutable database, role, schema, version, checksum, catalog-authority, profile, and evaluation-privilege sentinel on that same client, then takes a profile-and-entity lock. It permits only `PUBLIC`-inherited database temp, while refusing direct temp grants and all temporary-object SQL in the implementation. The runtime role has neither raw evaluation INSERT privilege nor permission to execute the evaluation persistence routine. Provider execution remains hard-disabled.
9. Keep `risely_agent_runtime_evaluation_writer` `NOLOGIN` and uncredentialed in production until its separately reviewed workload, network, secret, and lifecycle boundary exists. The ordinary credential operator does not provision it. In an isolated test only, provision a distinct credential, initialize `PostgresEvaluationWriter`, obtain its frozen branded result-store port, and verify that the production evaluation authority accepts it while rejecting runtime stores, inert stores, cloned ports, and caller-shaped lookalikes. The JavaScript writer verifies pinned Ed25519 signatures and exact authority output before calling the single atomic persistence routine. The routine admits only the evaluation-writer session role and independently enforces every recomputable candidate, judge, release, policy, gate, score, time, quorum, and relational invariant.
10. Run `node /app/canary/service/ceo-canary/src/retention.mjs` only as `risely_agent_runtime_migrator` on the documented cadence. Under one transaction and the maintenance lock, retention performs the complete post-migration attestation immediately before DML and again before commit. Any external trigger, foreign dependency, altered trigger, or catalog/ACL drift rolls back all deletion effects. Retention contains only schema-qualified mutations under `risely_agent_runtime` and must never target `public`, another QM schema, or an unqualified persistent relation.

Nothing deployed the earlier CEO-named database design. Version 8 is the sole initial migration for `risely_agent_runtime`: a preexisting `schema_migrations` table, any migration history, and every object in the bootstrapped schema are rejected rather than adopted. There is no compatibility, import, adoption, or backfill path.

The initial authority grant remains CEO-only and provider execution remains disabled. Version 8 persists and constrains the exact `profile_ref` plus `profile_sha256` composite identity, but the production registry still contains only the immutable CEO deployment profile. The inert synthetic test fixture validates cross-profile isolation without granting a second production identity. Future employee grants must reuse this shared schema and runtime and remain fail closed until their tenant, principal, organizational role, audience, grant, capability, provider-owner, evaluation-policy, migration evidence, and independent policy review are approved.

The structural integration is skipped unless `TEST_CANARY_PG16_DOCKER_BOOTSTRAP=1` is explicit. It creates one unique loopback-only PostgreSQL 16 container, proves exact `qm` creator authority and five-edge topology, confirms all four fixed roles remain `NOLOGIN`, and proves a refused rerun leaves the structural fingerprint unchanged. It accepts no URL.

For rotation, generate two new files under the same exact format, stop new canary work, invoke the credential operator once with both new files, and update the runtime and operator-only migration URL secret versions before resuming work. Never rotate only one role and never retain the old values in an environment, shell history, log, or artifact. The one provisioning transaction changes both roles or neither. The full isolated lifecycle proves the old credentials authenticate before rotation, provisions both replacements, proves both old credentials fail and both replacements authenticate, and uses the replacement migrator credential for all subsequent work.

The full lifecycle integration is skipped unless `TEST_CANARY_PG16_DOCKER_LIFECYCLE=1` is explicit. It proves ordinary credential provisioning, repeat provisioning, real rotation, and credential-reuse refusal while the evaluation writer remains outside that operator; refuses an enabled event trigger and `PUBLIC` foreign-data-wrapper `USAGE` before migration DDL; runs the real migration wrapper; then proves runtime routine execution is denied, provisions an isolated distinct evaluation-writer credential, obtains its authentic result-store port, verifies authority acceptance and forged-port rejection, and exercises a real candidate through signed judge quorum, atomic release persistence, and canonical outbox enqueue. It rejects a rewritten CHECK plus matching attacker-written fingerprint, a 64-bit sequence maximum changed by one, TOAST reloption drift, direct extension ownership of the canary schema, `PUBLIC` wrapper/server usage, and user mappings. It reproduces both an external `SECURITY DEFINER` deletion-trigger attack and an enabled event-trigger boundary, proving retention refuses each with the canary row intact and zero external effects, then runs clean retention. It accepts no caller database URL and removes every container, network, volume, image, and temporary file.
